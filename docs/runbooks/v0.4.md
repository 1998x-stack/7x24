# V0.4 operational runbook

## Setup

Upgrade existing V0.3 database in-place with `news24 db migrate`. This increments `user_version` to 2 while retaining news content and checkpoints. Make a consistent backup first. Run `news24 doctor --json`, `make test`, `make lint`, and `make typecheck`.

## Run and schedule

`news24 jobs install --collect-every 300 --probe-every 21600 --report-at 08:00 --timezone Asia/Shanghai` inserts three stable schedule IDs, without modifying them on repeated installation. Start one active worker with `news24 jobs run --loop --poll-seconds 5`. A single run `news24 jobs run` polls schedules and claims at most one task. Long-running operation supervision (systemd, containers) is deployment-specific; the CLI does not daemonize itself.

## Errors and retries

`jobs list` exposes PENDING/RETRY_WAIT/RUNNING/FAILED states (the initial state is QUEUED). The worker claims with a timed lease, raises errors on incomplete ingestion, and retries up to max_attempts. `news24 jobs recover` affects expired job leases only. Do not run `news24 db recover` while the original ingest is still running; the latter is a different V0.3 ingestion-run recovery command.

## Reporting

Generate day-scoped reports using `news24 report daily --date YYYY-MM-DD --timezone Asia/Shanghai`. `news24 report show --date YYYY-MM-DD` displays stored Markdown. The 08:00 scheduled report covers the preceding calendar day. Totals query all stored matching rows; the printed sample is capped. Coverage is UNVERIFIED, not a guarantee of all upstream news.

## API validation

`news24 source-probe` fetches one page from the Sina feed; it persists OK/EMPTY/STALE/ERROR and publication freshness data. Live endpoint, parameters, page and direction semantics need separate authorized network checks. Never interpret a page result or 200 status alone as full-day completeness.

## Regression and rollback

The new job and report tables are additive, so the original V0.3 data remains intact. The older V0.3 binary will refuse schema v2, by design. To revert the app safely, restore a consistent V0.3 database backup rather than trying to down-migrate user_version with existing V0.4 data.
