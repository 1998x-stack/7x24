# V0.3 transactional ingestion runbook

## Initial setup

Run `python -m pip install -e '.[dev]'`; `news24 doctor` tests the local FTS5-enabled SQLite runtime. Run `news24 db migrate --db data/news24.sqlite3` once; migration is idempotent. The CLI also migrates automatically before ingest.

## Incremental polling

`news24 ingest --source sina --category all --max-pages 50 --db data/news24.sqlite3`

Statuses: SUCCEEDED (inserted/updated), NO_CHANGES (successful but no changes), INCOMPLETE (partial pages stored, no highwater update), FAILED (error, no highwater update). An incomplete CLI run has exit code 3; a failure has exit code 1.

Start with larger page coverage when no checkpoint exists. Repeating a completed batch does not duplicate news or revisions. Each category has its own watermark.

## Historical range backfill

`news24 backfill --start 2026-03-01T00:00:00+08:00 --end 2026-03-03T00:00:00+08:00 --max-pages 100`

The time window is [start, end). A backfill never changes real-time checkpoint. Missing source publish time cannot be used as an early stop condition; payloads are still retained.

## Recovery

- Inspect `news24 db stats` and SQL `ingestion_runs` for any FAILED or INCOMPLETE runs.
- Repeat the last ingest after fixing source access or increasing max_pages.
- `news24 db recover` marks abandoned RUNNING records as FAILED; use only when no writer is active.
- To ensure consistent backup, use SQLite's backup API or `VACUUM INTO` on a quiescent database rather than copying a live WAL database file by itself.

## Scope and constraints

A single SQLite writer and advisory deployment lock is assumed. The upstream paging API is not versioned or guaranteed stable; page order errors fail closed. Long histories still use in-memory page lists (not streaming). Market sentiment and forecasts are outside V0.3. No automatic scheduling or web server in this stage.
